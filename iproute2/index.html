iproute2

Last update: 2026-08-28 10:51:46 +0800 +0800
tags: Linux | Networking | Netlink | Iproute2

iproute2 is the standard Linux userspace suite for inspecting and configuring the kernel networking stack. The suite covers links, addresses, routes, neighbours, tunnels, traffic control, sockets, hardware offload, and several specialized networking subsystems. Most commands exchange Netlink messages with the kernel; they do not implement the data plane that forwards packets.

The project publishes one release for each Linux kernel release. Matching versions expose the same generation of kernel interfaces, although a newer iproute2 can operate against an older kernel when it does not request unsupported features.

A History of Linux Userspace Network Management #

Linux network management developed in layers. Low-level utilities modify live kernel state, while configuration frameworks and daemons decide what state should persist and when to apply it.

PeriodSoftwareRole and Historical Significance
Early 1990sBSD-derived commands and net-toolsSeparate commands such as ifconfig, route, arp, and netstat became the conventional Linux interface for links, IPv4 addresses, routes, neighbour entries, and statistics. Their interfaces depend heavily on networking ioctls and /proc, so they cannot represent many later kernel features.
1990s onwardDistribution network scripts and ifupdownFiles such as Debian’s /etc/network/interfaces and distribution-specific network scripts added persistent configuration around low-level commands. ifup and ifdown describe interface lifecycle, but they are orchestration tools rather than kernel APIs.
Late 1990s onwardiproute2Alexey Kuznetsov created iproute2 alongside the kernel’s advanced routing, traffic-control, and RTnetlink work. ip consolidated the object model exposed by ifconfig, route, arp, and iptunnel; ss and tc covered socket inspection and traffic control. Netlink’s extensible, message-based interface allowed the suite to track new kernel capabilities.
2004 onwardNetworkManagerNetworkManager introduced a long-running connection manager for dynamic wired, Wi-Fi, mobile, and VPN connections. Connection profiles express desired state, while nmcli, nmtui, and graphical clients control the daemon.
2014 onwardsystemd-networkdsystemd 210 added a declarative network manager oriented toward boot-time and continuously managed links. .link, .netdev, and .network files define naming, virtual devices, addresses, routes, and related policy; networkctl provides runtime inspection and control.
2016 onwardNetplan and other configuration front endsNetplan added a YAML configuration layer that renders configuration for NetworkManager or systemd-networkd. Front ends of this class standardize policy without replacing the selected network-management daemon or the kernel interfaces beneath it.

The generations overlap because they solve different problems. ip addr add changes the running kernel immediately, whereas NetworkManager, systemd-networkd, or ifupdown owns persistent policy and may later replace that change. Administrators should avoid modifying a daemon-managed interface with ad hoc ip commands except for diagnosis or deliberate temporary state.

Packet filtering also follows a separate lineage: iptables and nft configure Netfilter rather than the routing and link objects managed by iproute2.

The ip Object Model #

ip uses the form ip [options] object command. The principal objects map to kernel networking concepts:

ObjectPurpose
linkinspect or configure network devices and link-layer properties
addressmanage IPv4 and IPv6 addresses
routemanage unicast, multicast, and special routes
rulemanage routing-policy database rules
neighbourmanage ARP and IPv6 neighbour-discovery entries
netnscreate and operate in named network namespaces
tunnel, l2tp, macsecconfigure tunnel and secure-link types
xfrmmanage IPsec state and policies
nexthopmanage reusable next-hop objects and groups
mptcpmanage Multipath TCP endpoints and limits
monitorstream RTnetlink state changes

The object list continues to grow because ip acts as a collection of front ends behind one executable. ip help lists top-level objects, and ip object help describes the commands supported by an installed release.

Choosing the Correct Layer #

  • Use iproute2 for immediate inspection, diagnostics, experiments, and low-level configuration that a higher-level manager does not expose.
  • Use NetworkManager, systemd-networkd, ifupdown, or a distribution configuration layer when state must survive reboot and react consistently to device lifecycle events.
  • Use nft for packet filtering and network address translation because those operations belong to Netfilter.
  • Match iproute2 documentation to the installed version because userspace can only encode features known at build time, and the running kernel can only accept features that it implements.
