Linux Kernel Build System

Last update: 2026-02-04 03:53:53 +0800 +0800
tags: Kbuild | Kernel | Linux | Makefiles

The Linux kernel uses GNU Make and Kbuild to configure, compile, link, and install the kernel and its modules. A normal build starts with a configuration target and then builds the default target:

sh 
make defconfig
make -j"$(nproc)"

The principal result is vmlinux, an ELF executable. Architectures may additionally produce bootable wrappers such as bzImage, zImage, or vmlinuz. Loadable modules are ELF relocatable objects linked into .ko files.

Source and Output Trees #

An in-tree build has identical srctree and objtree. An out-of-tree build keeps generated files separate:

sh 
mkdir build
make O=build defconfig
make -C build -j"$(nproc)"

make clean removes most generated files while retaining enough support for external modules. make mrproper also removes configuration and generated headers, and make distclean additionally removes editor backup and patch files.

Configuration #

make *config targets build and run a Kconfig front end, such as conf for oldconfig or mconf for menuconfig. Kconfig files distributed through the source tree define the option hierarchy. The selected values are written to .config and then transformed into include/config/auto.conf, include/generated/autoconf.h, and per-symbol files under include/config/.

The root Makefile determines SUBARCH from the host, accepts ARCH for a target architecture, and derives SRCARCH for source directories. Cross-compiles normally specify at least ARCH and a toolchain prefix or compiler.

Makefile Layers #

The root Makefile is the entry point. It includes architecture Makefiles and utility snippets such as scripts/Kbuild.include, scripts/Makefile.compiler, and configuration-dependent scripts/Makefile.* fragments. These snippets define shared functions, compiler flags, and rules rather than each subsystem’s object list.

Each source directory supplies a Makefile or, where necessary, a Kbuild file. Kbuild takes precedence. These files normally declare inputs rather than duplicate generic rules:

  • obj-y adds objects or subdirectories built into vmlinux.
  • obj-m adds loadable-module inputs.
  • lib-y and lib-m contribute archive members.
  • always-y names targets that should always be built.
  • hostprogs names tools built for the build host.

An object-list entry can name foo.o or foo/; the trailing slash requests recursive descent into that subdirectory. Configuration-controlled forms such as obj-$(CONFIG_FOO) += foo.o select an input when a symbol is y or m.

Subdirectory Builds #

The root build invokes a directory through:

makefile 
$(MAKE) $(build)=path/to/directory

build expands to -f scripts/Makefile.build obj, so this starts a sub-make using scripts/Makefile.build while passing the target directory as obj. That Makefile loads the directory’s Kbuild or Makefile, then scripts/Makefile.lib, which normalizes the declared variables and supplies generic compilation and archive rules. This division lets subsystem Makefiles focus on selecting sources. It also keeps dependencies local: a directory invokes a sub-make rather than reaching directly into another directory’s outputs.

scripts/Makefile.host supplies rules for host tools. The hostprogs-always-y shortcut adds host programs to the always-built set; a host program with no foo-objs, foo-cxxobjs, or Rust object list is compiled from its conventional single source.

Commands and Incremental Dependencies #

Kbuild names reusable recipes with cmd_<name> and concise quiet output with quiet_cmd_<name>. For example, $(call cmd,foo) runs cmd_foo and selects the quiet or verbose log according to V=.

The if_changed, if_changed_dep, and if_changed_rule helpers run a recipe when a prerequisite is newer, the command line has changed, or a target is missing. if_changed_dep additionally processes compiler dependency information. Generated hidden .cmd files record the saved command and dependencies for outputs such as objects, archives, generated headers, modules, and vmlinux. This makes a changed compiler option or Kconfig symbol a valid reason to rebuild an affected target, not just a changed source timestamp.

Link and Installation Results #

Directory objects are gathered into built-in.a archives for the built-in kernel or into module inputs. The final link creates vmlinux; architecture-specific rules may then wrap, compress, sign, or package it. Module post-processing resolves exported symbols, emits metadata, and produces .ko files. make modules_install installs modules and runs the installation rules, while architecture-specific install targets place the kernel image where the boot environment expects it.

Migrated Reference Material #

This article analyzes the building process of the Linux kernel, including the implementation of Makefiles. Various build-time generated files and build techniques are discussed.

It is well-known that the Linux kernel should be built by make *config followed by a make call without a goal. The make *config command does nothing more than invoke a wizard program, which may include compiling that wizard program first. It’s the wizard program’s responsibility to properly generate a .config file which holds the user’s choice on the kernel building configs.

The wizard program usually reads various Kconfig files in the source tree to determine what kernel build options are devised by the kernel developer, and in what structure these options should be displayed to an end user. The Kconfig system won’t be discussed as a part of a kernel’s build here. See this article for an intro to the syntax of a Kconfig file and the rules of writing one.

Before a build, it’s recommended to invoke 1 of the 3 clean targets:

  • clean: Remove most generated files but keep the config and enough build support to build external modules
  • mrproper (more proper): Remove all generated files + config + various backup files
  • distclean (clean for distribution): mrproper + remove editor backup and patch files

Out-of-source Build #

Linux supports out-of-source build by an O=dir make CLI argument:

sh 
cd linux-6.8.2
mkdir build
make O=build defconfig
cd build
make -j12

In the Makefile, the source directory is referred to by the $(srctree) variable while the build directory is the $(objtree). If the O=dir argument is not used, both will be the same.

A kernel build is initiated by calling a plain make on the build directory. This Makefile-based system also must support future repetitive invocation of make by detecting modifications and building only the necessary parts. The make interface is also versatile and assumes jobs of different nature (clean, generate configs, build modules, build the vmlinux), bringing complexity to the implementation of Makefiles.

We will be exploring how the Makefile pieces are put together to achieve this.

Overview #

The Makefile-based build system of Linux consists of 4 types of file:

  1. The root Makefile. It is the entrance of make execution.

  2. scripts/Kbuild.include and scripts/Makefile.*

    These are auxillary Makefile snippets that implement utilities and variables used by othe Makefiles, instead of defining build rules for the kernel.

  3. The Makefiles in each directory of source tree, including scripts/Makefile.

    These files append string values to certain well-known variables, including obj-y, obj-m, etc., rather than introducing new Makefile rules.

  4. Build time generated .<output_filename>.cmd and .<output_filename>.d in build tree, both being Makefile snipppets.

    They contain only Makefile rules (i.e. dependency) for <output_filename>.

The Root Makefile #

A lot about the mechanics can be learned by inspecting the root Makefile, the very first file a make process parses and executes.

The following pseudo-code briefly describes the root Makefile:

go 
func make_single(target) {
    include `scripts/Kbuild.include` for utils functions
    load ARCH SRCARCH etc. variables
    set compilerinclude path

    load include $(srctree)/scripts/Makefile.compiler

    if (target matches '*config') {
        // if this is a config build (i.e. we are generating .config)
        make -f `scripts/Kconfig/Makefile` *config
    } else {
        // non config build includes
        // 1. the actual vmlinuz or modules
        // 2. arch-specific targets
        // 3. clean
        // 4.

        load include/config/auto.conf (.config as Makefile variables)
        load $(srctree)/arch/$(SRCARCH)/Makefile
        load include/config/auto.conf.cmd

        compiler flag adjustment, depending on

        if (`make M=...` or `make KBUILD_EXTMOD=...` set) {
            `__all: modules`: default goal is to build `modules`
        } else {
            `__all: all`: default goal is to build `modules`
        }
    }
}


func make(targets, need-submake) {
    if (need-submake = 1) {
        make(targets, 0)
        return;
    }

    for each (target in targets)
        make_single(target)
}

scripts/Kbuild.include is included by many other Makefiles to provide utility functions. This section discusses the most commonly used ones.

cmd: print and execute commands #

makefile 
# $(call Cmd, foo):
# # With Echo Supressed:
# if `cmd_foo` exist,
# print either `quiet_cmd_foo` or `cmd_foo` value as string
# Trap Interrupt
# Call Cmd_foo
# Else
# No-op
cmd = @$(if $(cmd_$(1)),set -e; $($(quiet)log_print) $(delete-on-interrupt) $(cmd_$(1)),:)

The cmd function should be used when you want to call certain Makefile functions and print to the terminal a message. It will respect the make V=[1|2] argument and determine whether to print verbose messages. You see prettified one-line messages during a kernel build thanks to this function, e.g.:

  LDS     scripts/module.lds
  HOSTCC  usr/gen_init_cpio
  CC      init/main.o
  CC      certs/system_keyring.o
  CC      ipc/compat.o
  CC      mm/filemap.o
  AS      arch/x86/entry/entry.o
  CC      fs/open.o
  AR      arch/x86/virt/vmx/built-in.a

To write an operation that fits into this framework, define 2 variables:

  1. a cmd_xxx that holds the actual shell script; and
  2. a quiet_cmd_xxx varaible contains a short message
makefile 
quiet_cmd_makefile = GEN     Makefile
      cmd_makefile = { \
	echo "\# Automatically generated by $(srctree)/Makefile: don't edit"; \
	echo "include $(srctree)/Makefile"; \
	} > Makefile

kbuild-file: get the path to the Makefile or Kbuild file under $(src) #

makefile 
### # The Path to Kbuild or Makefile. Kbuild Has Precedence over Makefile.
kbuild-dir = $(if $(filter /%,$(src)),$(src),$(srctree)/$(src))
kbuild-file = $(or $(wildcard $(kbuild-dir)/Kbuild),$(kbuild-dir)/Makefile)

The caller must define an src variable before calling kbuild-file, which must be a directory name without the trailing slash.

For example:

makefile 
# Snippet from: scripts/Makefile.build
# Obj Is an Export-ed Variable to This Submake
src := $(obj)

# Later ...
# include `$(obj)/Kbuild` or `$(obj)/Makefile`
include $(kbuild-file)
  • kbuild-file expands to the absolute path to the Kbuild file, or if absent, the Makefile, under src.
  • kbuild-dir is a helper macro never used independently.

Use these macros, instead of hardcoding $(src)/Makefile, for compatibility. Historically Makefile pieces shattered in each directory have the file name Kbuild. Almost all of them have been renamed to Makefile by the time of this writing, but some old device drivers may be still using Kbuild.

$(build): standard way of invoking sub-make #

$(Q)$(MAKE) $(build)=<dir> is the recommended way to invoke make in a subdirectory. ($(Q) expands to @ or empty, determining whether to echo the recipe.)

You will see recipes like the following one pervasively in Makefiles:

makefile 
%config: outputmakefile scripts_basic FORCE
	$(Q)$(MAKE) $(build)=scripts/kconfig $@

build is defined as:

makefile 
### # Shorthand for $(Q)$(MAKE) -F scripts/Makefile.build obj=
# Usage:
# $(Q)$(MAKE) $(build)=dir
build := -f $(srctree)/scripts/Makefile.build obj

That is, without changing the current working directory, $(MAKE) $(build)=dir some-target uses scripts/Makefile.build as the Makefile, and executes its some-target goal with an obj=dir argument, where dir must be a directory name without the trailing slash. Most often, executing the default goal is desired, so some-target is omitted.

if_changed_*: #

makefile 
### # If_changed      - Execute Command If Any Prerequisite Is Newer Than
# Target, or Command Line Has Changed
# If_changed_dep  - as If_changed, but Uses Fixdep to Reveal Dependencies
# Including Used Config Symbols
# If_changed_rule - as If_changed but Execute Rule Instead
# See Documentation/kbuild/makefiles.rst for More Info
# Usage: $(call if_changed_rule,foo)
# Will Check If $(cmd_foo) or Any of the Prerequisites Changed,
# And If So Will Execute $(rule_foo).
if_changed_rule = $(if $(if-changed-cond),$(rule_$(1)),@:)

# Execute the Command and Also Postprocess Generated .D Dependencies File.
if_changed_dep = $(if $(if-changed-cond),$(cmd_and_fixdep),@:)

if-changed-cond = $(newer-prereqs)$(cmd-check)$(check-FORCE)

# Find Any Prerequisites That Are Newer Than Target or That Do Not Exist.
# PHONY Targets Skipped in Both Cases.
# If There Is No Prerequisite Other Than Phony Targets, $(newer-prereqs) Becomes
# Empty Even If the Target Does Not Exist. Cmd-check Saves This Corner Case.
newer-prereqs = $(filter-out $(PHONY),$?)

scripts/Makefile.build: the module builder #

The purpose of scripts/Makefile.build is to make life easier for kernel module maintainers, such that only variable definition, and no rule, needs to be defined in a module-specific Makefile (rules can be added for documented behavior, see below).

When building a kernel subdirectory, the recommended $(MAKE) $(build)=dir syntax always runs a sub-make with the Makefile scripts/Makefile.build (via the -f option, see build for detail).

Among other scripting, this file includes the $(kbuild-file) (i.e. the Makefile in the dir as given in $(build)=dir, see kbuild-file for detail), and load a scripts/Makefile.lib to normalize the variables defined in the $(kbuild-file):

makefile 
# scripts/Makefile.build
# Init Variables, Load Util Functions, Load Compiler Setups ...
include $(kbuild-file)
include $(srctree)/scripts/Makefile.lib

# Do Not Include Hostprogs Rules Unless Needed.
# $(sort ...) Is Used Here to Remove Duplicated Words and Excessive Spaces.
hostprogs := $(sort $(hostprogs))
ifneq ($(hostprogs),)
include $(srctree)/scripts/Makefile.host
endif

SUBARCH, ARCH, and SRCARCH #

Some variables are first setup in the Makefile at the very beginning of a make build. They are passed to Kconfig and Kbuild such that the generation of kernel config wizard works properly.

SUBARCH by the shell script in the scripts/subarch.include:

makefile 
# Root Makefile:
# Include $(srctree)/scripts/subarch.include
# SUBARCH Tells the Usermode Build What the Underlying Arch Is.  That Is Set
# First, and If a Usermode Build Is Happening, the "ARCH=um" on the Command
# Line Overrides the Setting of ARCH Below.  If a Native Build Is Happening,
# Then ARCH Is Assigned, Getting Whatever Value It Gets Normally, And
# SUBARCH Is Subsequently Ignored.
SUBARCH := $(shell uname -m | sed -e s/i.86/x86/ -e s/x86_64/x86/ \
				  -e s/sun4u/sparc64/ \
				  -e s/arm.*/arm/ -e s/sa110/arm/ \
				  -e s/s390x/s390/ \
				  -e s/ppc.*/powerpc/ -e s/mips.*/mips/ \
				  -e s/sh[234].*/sh/ -e s/aarch64.*/arm64/ \
				  -e s/riscv.*/riscv/ -e s/loongarch.*/loongarch/)

The ARCH variable defaults to $(SUBARCH) if not explicitly given on the CLI as make ARCH=...:

makefile 
ARCH		?= $(SUBARCH)

Using an explicit make ARCH=... is mandatory if you are cross-compiling the kernel for a different CPU architecture.

SRCARCH is derived from ARCH and is precisely one of the subdirectory names in arch/:

makefile 
SRCARCH 	:= $(ARCH)

# Additional ARCH Settings for X86
ifeq ($(ARCH),i386)
        SRCARCH := x86
endif
ifeq ($(ARCH),x86_64)
        SRCARCH := x86
endif

# Additional ARCH Settings for Sparc
ifeq ($(ARCH),sparc32)
       SRCARCH := sparc
endif
ifeq ($(ARCH),sparc64)
       SRCARCH := sparc
endif

# Additional ARCH Settings for Parisc
ifeq ($(ARCH),parisc64)
       SRCARCH := parisc
endif

SRCARCH is used whenever architecture-dependent sources need to be referenced in the Makefiles or Kconfig files:

sh 
# arch/Kconfig
# Note: arch/$(SRCARCH)/Kconfig Needs to Be Included First So That It Can
# Override the Default Values in This File.
# Source "arch/$(SRCARCH)/Kconfig"

Techniques: Ensure a File Has Been Generated #

file-name target with no dependency is considered always up-to-date, unless that file doesn’t exist (i.e. effectively becomes a PHONY):

makefile 
# $(KCONFIG_CONFIG) defaults to `.config`.
# Whenever make finds that the `.config` file doesn't exist thus the recipe needs to be executed, it's a problem
$(KCONFIG_CONFIG):
	@echo >&2 '***'
	@echo >&2 '*** Configuration file "$@" not found!'
	@echo >&2 '***'
	@echo >&2 '*** Please run some configurator (e.g. "make oldconfig" or'
	@echo >&2 '*** "make menuconfig" or "make xconfig").'
	@echo >&2 '***'
	@/bin/false
--- end ---
