Docker-based Hadoop/Spark/Hive Orchestration

Last update: 2026-07-24 08:48:16 +0800 +0800
tags: Hadoop | Spark | Hive | Docker

Hadoop, Spark, and Hive have overlapping Java, Hadoop-client, and configuration requirements. Installing every distribution on a workstation also mixes cluster state with host files. A Docker Compose lab avoids both problems by mounting an immutable software tree at /opt/ro and placing daemon state in named volumes.

The guide builds the lab in five stages:

  1. Start an offline toolbox with the JDK, Hadoop, Hive, and Spark commands but no cluster daemons.
  2. Add one HDFS NameNode and three DataNodes.
  3. Add one YARN ResourceManager and three NodeManagers.
  4. Add HiveServer2 with an embedded Derby metastore.
  5. Run Spark locally and on YARN.

Every container receives two read-only bind mounts:

  • /opt/ro contains extracted binary distributions and stable symlinks.
  • /opt/conf contains the shared environment script and XML configuration.

Named volumes hold HDFS, YARN, Hive, and toolbox state. Temporary files and daemon logs use container tmpfs mounts because Compose captures foreground-process output through docker compose logs.

The topology demonstrates process boundaries, HDFS replication, YARN scheduling, HiveServer2, and Spark submission. Three DataNodes on one physical host do not provide fault tolerance because a host failure still removes every replica.

Treat Version Compatibility as a Manifest Decision #

Do not infer compatibility from a version number or from a successful process launch. Before downloading a combination, verify all of the following against the official release notes and documentation for the exact releases:

  1. The JDK version and CPU architecture supported by Hadoop, Spark, and Hive.
  2. The Hadoop client line against which the Spark without-hadoop distribution was built and tested.
  3. The Hadoop and execution-engine versions supported by Hive.
  4. Any required JVM module flags, removed components, or changed configuration properties.
  5. Whether the binary archives contain the example and client JARs used by the validation commands.

The paths below preserve one concrete example manifest. They are examples rather than a compatibility claim:

text

├── hadoop-3.5.0/
├── hive -> apache-hive-4.2.0-bin

├── jdk17 -> zulu17.58.21-ca-jdk17.0.15-linux_aarch64

├── spark -> spark-4.1.2-bin-without-hadoop

Replace the symlink targets with a combination verified for the intended host architecture. Keep the stable symlink names because the remaining configuration refers only to /opt/ro/jdk17, /opt/ro/hadoop, /opt/ro/hive, and /opt/ro/spark.

The Compose image supplies a Linux userspace, not Java or Hadoop. An air-gapped host must already contain debian:bookworm-slim, for example through docker load, in addition to the files under ro/.

Add the Shared Environment Script #

Save the following script as conf/init.sh:

bash 
#!/usr/bin/env bash
set -euo pipefail

export JAVA_HOME=/opt/ro/jdk17
export HADOOP_HOME=/opt/ro/hadoop
export HADOOP_COMMON_HOME="$HADOOP_HOME"
export HADOOP_HDFS_HOME="$HADOOP_HOME"
export HADOOP_MAPRED_HOME="$HADOOP_HOME"
export HADOOP_YARN_HOME="$HADOOP_HOME"
export HADOOP_CONF_DIR=/opt/conf/hadoop
export YARN_CONF_DIR="$HADOOP_CONF_DIR"
export HIVE_HOME=/opt/ro/hive
export HIVE_CONF_DIR=/opt/conf/hive
export SPARK_HOME=/opt/ro/spark

export HADOOP_LOG_DIR=/var/log/hadoop
export YARN_LOG_DIR=/var/log/hadoop
export HADOOP_PID_DIR=/run/hadoop
export YARN_PID_DIR=/run/hadoop
export HIVE_LOG_DIR=/var/log/hive

# Hive must precede Spark because both distributions can contain "beeline".
export PATH="$HIVE_HOME/bin:$SPARK_HOME/bin:$HADOOP_HOME/bin:$HADOOP_HOME/sbin:$JAVA_HOME/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
export LD_LIBRARY_PATH="$HADOOP_HOME/lib/native${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"

# A Spark "without-hadoop" archive needs the selected Hadoop client's JARs.
if [[ -z "${SPARK_DIST_CLASSPATH:-}" ]]; then
  export SPARK_DIST_CLASSPATH="$("$HADOOP_HOME/bin/hadoop" classpath)"
fi

wait_for_port() {
  local host="$1"
  local port="$2"
  local timeout="${3:-120}"
  local deadline=$((SECONDS + timeout))

  until (echo >"/dev/tcp/${host}/${port}") >/dev/null 2>&1; do
    if ((SECONDS >= deadline)); then
      echo "Timed out waiting for ${host}:${port}" >&2
      return 1
    fi
    sleep 2
  done
}

wait_for_hdfs() {
  local timeout="${1:-180}"
  local deadline=$((SECONDS + timeout))
  local status

  until status="$(hdfs dfsadmin -safemode get 2>/dev/null)" &&
    grep -q "Safe mode is OFF" <<<"$status"; do
    if ((SECONDS >= deadline)); then
      echo "Timed out waiting for writable HDFS" >&2
      return 1
    fi
    sleep 3
  done
}

wait_for_yarn_nodes() {
  local expected="${1:-1}"
  local timeout="${2:-180}"
  local deadline=$((SECONDS + timeout))
  local output
  local running

  while true; do
    output="$(yarn node -list -all 2>/dev/null || true)"
    running="$(awk '$0 ~ /RUNNING/ { count++ } END { print count + 0 }' <<<"$output")"
    if ((running >= expected)); then
      return 0
    fi
    if ((SECONDS >= deadline)); then
      echo "Timed out waiting for ${expected} YARN NodeManagers; found ${running}" >&2
      return 1
    fi
    sleep 3
  done
}

Every service sources the same file, so daemon and client processes use the same Java installation, Hadoop configuration, and binary ordering.

No hive.metastore.uris property is present because HiveServer2 opens Derby in-process. Derby embedded mode permits only one process to own the database, so do not run a second HiveServer2, hive CLI, or standalone metastore against the same volume. Beeline remains safe because it connects to HiveServer2 over JDBC rather than opening Derby.

The example selects MapReduce as Hive’s execution engine to reuse the YARN services already in the lab. Confirm that the chosen Hive release still ships and supports that engine; otherwise install and configure an execution engine documented for that release.

depends_on controls container creation order only. DataNodes, NodeManagers, and HiveServer2 also use active readiness loops because a started container does not imply that its daemon socket or distributed service is ready.

The NameNode formats its volume only when current/VERSION is absent. Restarts therefore preserve the namespace rather than formatting it again.

Stage 1: Start the Offline Toolbox #

Start only the toolbox:

sh 
docker compose up -d toolbox
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  java -version
  hadoop version
  hive --version
  spark-submit --version
  command -v beeline
'

HDFS and YARN commands load their cluster configuration, but no daemon is running yet. The stage remains useful for inspecting classpaths and running computations that do not access HDFS:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  spark-submit \
    --master "local[2]" \
    --class org.apache.spark.examples.SparkPi \
    "$SPARK_HOME"/examples/jars/spark-examples_*.jar \
    10
'

The command should print a Pi is roughly ... result from Spark’s example application. Failure before Spark creates its context generally indicates a Java, architecture, or classpath mismatch rather than an HDFS problem.

Stage 2: Start HDFS #

Start the NameNode and all three DataNodes:

sh 
docker compose up -d namenode datanode1 datanode2 datanode3

Wait for HDFS to leave safe mode, inspect the DataNode report, and perform a write/read cycle:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  wait_for_hdfs 180
  hdfs dfsadmin -report
  hdfs dfs -mkdir -p /tmp /user/root/lab
  hdfs dfs -chmod 1777 /tmp
  printf "hdfs-ok\n" > /work/hdfs-check.txt
  hdfs dfs -put -f /work/hdfs-check.txt /user/root/lab/
  hdfs dfs -cat /user/root/lab/hdfs-check.txt
'

The report should list three live DataNodes. Open http://127.0.0.1:9870/ for the NameNode UI.

Stage 3: Start YARN #

Start the ResourceManager and all three NodeManagers:

sh 
docker compose up -d \
  resourcemanager \
  nodemanager1 nodemanager2 nodemanager3

Wait for all workers and submit the bundled MapReduce pi example:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  wait_for_yarn_nodes 3 180
  yarn node -list -all
  hadoop jar \
    "$HADOOP_MAPRED_HOME"/share/hadoop/mapreduce/hadoop-mapreduce-examples-*.jar \
    pi 2 10
'

Open http://127.0.0.1:8088/ to inspect the application, containers, and NodeManagers. A process that runs entirely in the toolbox does not validate YARN; the ResourceManager UI or yarn application -list -appStates ALL must show the submitted application.

Stage 4: Start HiveServer2 #

Start the single HiveServer2 process:

sh 
docker compose up -d hiveserver2

HiveServer2 waits for writable HDFS and at least one running NodeManager, creates warehouse directories, initializes the Derby schema when necessary, and then starts its Thrift endpoint. Wait for the endpoint before invoking Beeline:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  wait_for_port hiveserver2 10000 240
  beeline \
    -u jdbc:hive2://hiveserver2:10000/default \
    -n root \
    --silent=true \
    -e "
      CREATE TABLE IF NOT EXISTS lab_numbers (n INT);
      INSERT INTO lab_numbers VALUES (1), (2), (3);
      SELECT SUM(n) AS total FROM lab_numbers;
    "
'

The final query should return 6. DDL success validates HiveServer2, Derby, and the HDFS warehouse. The insert and aggregation also validate the configured execution path. Consult the HiveServer2 and YARN logs if DDL succeeds but the query engine fails.

Stage 5: Run Spark on YARN #

Run the same Spark example through YARN:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  wait_for_yarn_nodes 3 180
  spark-submit \
    --master yarn \
    --deploy-mode client \
    --conf spark.executor.instances=2 \
    --conf spark.executor.cores=1 \
    --conf spark.executor.memory=512m \
    --conf spark.driver.memory=512m \
    --class org.apache.spark.examples.SparkPi \
    "$SPARK_HOME"/examples/jars/spark-examples_*.jar \
    10
'

YARN should allocate an ApplicationMaster and two executors. Confirm completion independently:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  yarn application -list -appStates ALL
'

Understand SPARK_DIST_CLASSPATH and PATH Precedence #

A Spark without-hadoop archive omits the Hadoop client JARs. Spark reads SPARK_DIST_CLASSPATH, so the environment script populates it from the selected Hadoop distribution:

sh 
export SPARK_DIST_CLASSPATH="$(hadoop classpath)"

The setting lets the Spark submission client load YARN and HDFS classes while preserving a single Hadoop installation under /opt/ro/hadoop. Spark uploads or references its own application artifacts through YARN; NodeManagers inherit the same JAVA_HOME and Hadoop environment from their daemon process.

Some Spark distributions also contain a beeline launcher, but a without-hadoop archive may not contain the Hive classes expected by that launcher. Placing $HIVE_HOME/bin before $SPARK_HOME/bin ensures that an unqualified beeline command uses Hive’s client:

sh 
command -v beeline
# /opt/ro/hive/bin/beeline

Spark’s own scripts remain unambiguous because spark-submit, spark-shell, and their internal relative launchers come from $SPARK_HOME.

Persistence and Targeted Reset #

docker compose down removes containers and the dedicated network but retains every named volume:

sh 
docker compose down

Starting the services again reuses the HDFS namespace, DataNode blocks, ResourceManager recovery state, NodeManager local state, Derby database, and toolbox files.

Reset only the subsystem whose state is invalid:

sh 
# Reset Hive metadata and HiveServer2-local Hadoop scratch state.
docker compose stop hiveserver2
docker compose rm -f hiveserver2
docker volume rm \
  hadoop-lab-hiveserver2-state \
  hadoop-lab-hiveserver2-hadoop-state

# Reset YARN state without deleting HDFS or Hive.
docker compose stop resourcemanager nodemanager1 nodemanager2 nodemanager3
docker compose rm -f resourcemanager nodemanager1 nodemanager2 nodemanager3
docker volume rm \
  hadoop-lab-resourcemanager-state \
  hadoop-lab-nodemanager1-state \
  hadoop-lab-nodemanager2-state \
  hadoop-lab-nodemanager3-state

# Reset HDFS as one consistency unit.
docker compose stop namenode datanode1 datanode2 datanode3
docker compose rm -f namenode datanode1 datanode2 datanode3
docker volume rm \
  hadoop-lab-namenode-state \
  hadoop-lab-datanode1-state \
  hadoop-lab-datanode2-state \
  hadoop-lab-datanode3-state

Resetting only the NameNode or only a DataNode can leave incompatible cluster IDs or orphaned block state. Remove all four HDFS volumes together when a fresh filesystem is required. None of the commands above deletes unrelated Docker volumes or host directories.

Troubleshooting #

UID and Volume Permissions #

The Compose file defaults to UID and GID 0 because a stock read-only Debian image has no matching lab account and Docker creates named volumes as root. The containers remain isolated from host bind-mounted write paths, but root inside a container is still unsuitable for production.

To run with another numeric identity, set both variables and make each service volume writable by that identity. A narrowly scoped repair for an existing NameNode volume is:

sh 
LAB_UID=1000 LAB_GID=1000 \
docker compose run --rm --user 0:0 --entrypoint bash namenode \
  -lc 'chown -R 1000:1000 /var/lib/hadoop'

Repeat the operation only for the affected service volumes. A purpose-built image with a real passwd entry for the chosen UID is preferable because Hadoop and YARN may query operating-system user and group information.

CPU Architecture Mismatch #

The JDK under /opt/ro must be a Linux build for the container architecture. A macOS JDK cannot run in a Linux container, and an AArch64 JDK cannot run in an AMD64 container without matching emulation:

sh 
docker compose run --rm --entrypoint bash toolbox -lc '
  uname -m
  dpkg --print-architecture
  /opt/ro/jdk17/bin/java -version
'

An Exec format error indicates a binary for the wrong architecture or operating system. Select archives for the same architecture or set an explicitly supported Docker platform and accept the cost and limitations of emulation.

Hostname and Configuration Errors #

Errors such as UnknownHostException, DataNode registration failures, or YARN clients connecting to localhost indicate inconsistent service names or configuration mounts. Inspect resolution and active configuration from the toolbox:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  getent hosts namenode resourcemanager hiveserver2
  hdfs getconf -confKey fs.defaultFS
  yarn getconf -confKey yarn.resourcemanager.hostname
'

Keep Compose service names, hostname values, fixed addresses, and XML hostnames aligned. Recreate containers after changing a read-only configuration file:

sh 
docker compose up -d --force-recreate

Memory and Stalled Allocations #

Three NodeManagers advertise 1536 MiB each, while Hadoop, Hive, Spark, and Docker also require memory. Allocate enough memory to the Docker runtime, then inspect pending requests:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  yarn node -list -all
  yarn application -list -appStates ACCEPTED,RUNNING
'

Reduce Spark executor count or memory before increasing YARN’s advertised capacity. Advertised YARN memory does not create physical memory.

Logs and Failed Containers #

Foreground daemons send their primary output to Compose:

sh 
docker compose ps
docker compose logs --tail=200 namenode
docker compose logs --tail=200 nodemanager1
docker compose logs --tail=200 hiveserver2

Application diagnostics are also available through YARN:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  yarn application -list -appStates ALL
  yarn logs -applicationId APPLICATION_ID
'

Replace APPLICATION_ID with the identifier reported by YARN.

Derby Schema Initialization #

An interrupted first start can leave a partial Derby schema. Inspect the error before deleting anything:

sh 
docker compose run --rm --no-deps --entrypoint bash hiveserver2 -lc '
  source /opt/conf/init.sh
  schematool -dbType derby -info
'

If the database contains no needed metadata and schema initialization cannot recover, reset only hadoop-lab-hiveserver2-state as described above. Do not start another process against the same embedded Derby directory.

Java Compatibility #

UnsupportedClassVersionError, module-access failures, removed Java APIs, or native-library errors indicate an unsupported release combination. Capture the exact versions:

sh 
docker compose exec toolbox bash -lc '
  source /opt/conf/init.sh
  java -version
  hadoop version
  hive --version
  spark-submit --version
'

Resolve the mismatch by selecting a combination documented by the component maintainers. Do not add broad JVM --add-opens flags or replace JARs until the relevant release documentation requires that change.

Security and Production Boundaries #

The lab deliberately omits controls required by a production deployment:

  • Hadoop uses simple authentication rather than Kerberos.
  • HiveServer2 accepts unauthenticated connections and does not use TLS.
  • HDFS and YARN authorization policies are not hardened.
  • HiveServer2 impersonation is disabled.
  • Derby provides no concurrent metastore service or external backup strategy.
  • Daemons run as root by default inside containers.
  • Published ports bind to loopback, but every container on hadoop-lab-net can reach the services.
  • HDFS replicas and YARN workers share one Docker host.
  • Images and mounted archives are not pinned by digest or verified by checksum in Compose.
  • Resource limits, monitoring, secret management, high availability, and rolling upgrades are absent.

Use the topology for local integration work and protocol inspection. A production cluster requires authenticated services, separate hosts or failure domains, a supported external metastore database, non-root identities, durable logging, resource isolation, and a compatibility matrix maintained with each upgrade.
