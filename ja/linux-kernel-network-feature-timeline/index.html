カーネルとユーザー空間の境界 #

Linuxにはadd_route()やcreate_veth()のようなシステムコールはありません。代わりに、ユーザー空間はカーネル制御インターフェースを選択し、汎用システムコールを介してアクセスします。特にNetlinkは、システムコールではなく、ソケットプロトコルのファミリーです。

SyscallsControl InterfaceNetwork Configuration RoleCurrent Guidance
socket(), bind(), sendmsg(), and recvmsg()NetlinkプロセスはAF_NETLINKソケットを開き、Netlinkファミリーと構造化メッセージを交換します。NETLINK_ROUTEは、リンク、アドレス、ルート、近隣、トラフィック制御、および関連オブジェクトを設定します。Generic Netlinkとサブシステムプロトコルは、nftables、nl80211、ethtool、devlink、WireGuardなどを対象とします。システム全体のネットワーク設定には、該当するNetlinkファミリーを優先します。メッセージ属性、確認応答、マルチパート応答、APIの進化には慎重な処理が必要なため、保守されているライブラリまたはツールを使用します。

推奨インターフェースの変化 #

  1. 初期のLinuxではioctl、ソケットオプション、仮想ファイルが使用されていました。 ifconfig、route、arpなどのプログラムは、ネットワークデバイスおよびルーティングioctlを発行していました。/proc/sys/netはグローバルなチューナブルを提供し、旧来のiptablesによるファイアウォール世代ではプロトコル固有のソケットオプションが使用されていました。
  2. Rtnetlinkが拡張可能なネットワーク制御プレーンになりました。 Linux 2.2は、NETLINK_ROUTEを介してリンク、複数のアドレス、ルート、近隣、トラフィック制御オブジェクトを公開しました。そのため、iproute2ツール（ip、bridge、tc）は、新しい設定においてioctl指向のnet-toolsコマンドを置き換えました。
  3. サブシステム固有のNetlinkファミリーが固定プライベートABIを置き換えました。 Generic Netlinkおよび関連プロトコルによって、システムコールを変更せずにコマンドとtype-length-value属性を進化させられるようになりました。nl80211はWireless Extensionsを、nftablesは旧来のiptablesルールABIを置き換え、新しいethtool操作ではデバイスioctlではなくNetlinkが使用されます。
  4. eBPFがプログラム可能なデータプレーン境界を追加しました。 bpf()システムコールはプログラムとマップを管理しますが、設定はアタッチポイントごとに分かれています。rtnetlinkはトラフィック制御と既存のXDPアタッチメントを設定し、ソケットオプションは従来のソケットフィルターをアタッチし、BPFリンクは対応するフックに対してファイルディスクリプターによる有効期間管理を提供します。
  5. 新しい制御プレーンは記述されたNetlink APIを優先します。 現在のカーネルネットワーキング開発では、機械可読な仕様によってNetlinkファミリーを文書化しています。アプリケーションはこれらのAPIを使用し、確認応答と拡張確認応答を要求し、対応する構造化された代替がないインターフェースに限ってioctlまたはテキストファイル解析を使用すべきです。

対応するUAPIの詳細については、カーネルのNetlink入門、rtnetlink(7)、netdevice(7)、bpf(2)ドキュメントを参照してください。

Rtnetlink #

rtnetlinkのrtはroutingを意味しますが、このインターフェースはカーネルの汎用ネットワーク制御プロトコルへと拡張されています。プロセスはsocket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE)を開き、RTM_*メッセージを送信します。各メッセージには、struct nlmsghdr、オブジェクト固有の固定ヘッダー、アラインメントされたtype-length-value属性が含まれます。

Rtnetlinkは、次の3種類のやり取りをサポートします。

  • Do request: 1つのオブジェクトを作成、置換、変更、削除し、確認応答を受信します。
  • Dump request: すべてのリンクやすべてのルートなど、オブジェクトクラスを列挙します。カーネルはNLMSG_DONEで終了するマルチパート応答を返します。
  • Multicast notification: リンク、アドレス、ルート、近隣、ルール、トラフィック制御などの変更についてグループを購読します。通知では返信と同じオブジェクトメッセージを使用するため、プログラムはローカルキャッシュを維持できます。

アプリケーションはNETLINK_EXT_ACKも有効にすべきです。拡張確認応答は、拒否された属性を特定し、人間が読めるカーネルメッセージを含め、ポリシー制約を報告できます。成功した確認応答は、カーネルがそのメッセージを処理したことを意味しますが、個別のrtnetlink要求のシーケンスがトランザクショナルになることは意味しません。

名前空間と一貫性モデル #

rtnetlinkソケットは、それが関連付けられているネットワーク名前空間で動作します。そのため、ほとんどの要求は、その名前空間のリンク、ルート、ルール、近隣、トラフィック制御オブジェクトだけを参照および変更します。リンク属性によってデバイスを別の名前空間に移動でき、名前空間IDメッセージによってピア名前空間への参照を作成できます。

変更要求では通常、対象ネットワーク名前空間を所有するユーザー名前空間内のCAP_NET_ADMINが必要です。機密性のあるデバイスまたはプロトコル情報を公開する読み取り要求も制限される場合があります。

ダンプはアトミックなスナップショットではありません。マルチパートダンプの進行中にオブジェクトが変更される可能性があり、受信バッファーがオーバーフローするとマルチキャスト通知が失われる場合があります。状態同期器は次の処理を行うべきです。

  1. 必要なマルチキャストグループにソケットを開いてバインドします。
  2. 一意のシーケンス番号でダンプを要求します。
  3. シーケンス番号と送信元ポートIDによってユニキャスト返信を照合します。
  4. ダンプ中に到着した通知を処理します。
  5. ENOBUFS、中断されたダンプ、不正な属性を検出します。
  6. 同期を証明できない場合はキャッシュを破棄し、ダンプを再実行します。

ユーザー空間ネットワークユーティリティ #

Linuxには、単一のユーザー空間ネットワークスタックはありません。コマンドラインツール、ポリシーデーモン、設定レンダラー、ルーティングデーモン、コンテナプラグインは、異なるカーネル制御インターフェースにアクセスします。そのため、高水準コマンドはカーネルではなくデーモンを制御する場合があります。

SoftwarePrimary RolePath to the Kernel
iproute2ipはリンク、アドレス、ルート、ルール、近隣、ネットワーク名前空間を管理し、bridgeはブリッジ状態を管理し、tcはトラフィック制御を管理し、ssはソケットを検査します。プログラムはiproute2の内部Netlinkサポートを直接使用します。ほとんどの設定はrtnetlinkを通過し、ソケット検査には診断用Netlinkファミリーを使用します。iproute2は実行可能ファイルのスイートであり、他のネットワークマネージャーが必要とするデーモンではありません。
NetworkManagerEthernet、Wi-Fi、モバイルブロードバンド、VPN、IP設定、DNS統合の接続プロファイルとポリシーを維持します。nmcli、nmtui、デスクトップアプレット、アプリケーションはクライアントです。nmcliはlibnmを使用して、D-Bus経由でNetworkManagerデーモンを呼び出します。デーモンのLinuxプラットフォーム層は通常のリンク、アドレス、ルート、ルール、トラフィック制御操作のためにNetlinkソケットを直接開き、これらの操作をip実行ファイル経由では送信しません。オプションのヘルパーは、Wi-Fi認証、PPP、DHCP、DNS、ファイアウォール統合などを処理します。
systemd-networkd宣言的な.network、.netdev、.link設定を適用し、DHCPおよびルーター検出クライアントを実行し、ネットワーク状態を維持します。networkctlは検査および制御用CLIです。systemd-networkdはsystemd内部のNetlink実装を使用してカーネルを設定します。networkctlは管理対象設定でiproute2を呼び出すのではなく、networkdのAPIと状態を使用します。
NetplanディストリビューションレベルのYAMLをバックエンド設定に変換し、その設定の適用を調整します。NetplanはNetworkManagerまたはsystemd-networkdをレンダラーとして選択します。継続的なカーネル設定を実行するのは、NetplanのYAMLパーサーではなく選択されたデーモンです。
nftablesnftはファイアウォール、NAT、パケット分類、集合またはマップのルールを作成します。libnftablesはアプリケーションに同じエンジンを公開します。nftはlibnftablesとlibnftnlを使用し、NETLINK_NETFILTERを介してnftablesサブシステムとバッチメッセージを交換します。rtnetlinkまたはiproute2は使用しません。
firewalld動的なファイアウォールゾーン、サービス、ポリシー、実行時設定と永続設定を維持します。firewall-cmdは主要CLIです。firewall-cmdはD-Bus経由でfirewalldデーモンを呼び出します。デーモンは通常、NetworkManagerまたはiproute2にルールのインストールを依頼するのではなく、nftablesバックエンドを通じてルールを適用します。
ethtoolリンクモード、チャネル、リング、コアレッシング、オフロード、RSS、統計、ファームウェアデータなど、ドライバーとNICのプロパティを読み取り、変更します。新しい操作ではethtool Generic Netlinkファミリーを使用します。古い操作またはまだ変換されていない操作ではSIOCETHTOOL ioctlを使用するため、選択される経路はコマンドとカーネルの対応状況に依存します。
iw802.11物理デバイス、仮想インターフェース、チャネル、ステーション、スキャン、省電力、規制状態を検査および設定します。iwはnl80211 Generic Netlinkファミリーにコマンドを送信します。ipを呼び出しませんが、生成されたインターフェースの通常のリンクおよびIP層設定は引き続きipが担当します。
wpa_supplicant and iwdWi-Fiのスキャン、認証、アソシエーション、ローミング、鍵管理を実行します。各デーモンはnl80211を通じてcfg80211/mac80211を制御します。NetworkManagerはD-Bus経由でいずれかのデーモンを制御でき、Wi-Fiデーモンがその後カーネルと通信します。
conntrack-toolsNetfilterのコネクショントラッキング状態を一覧表示、変更、監視、複製します。conntrackとconntrackdは、rtnetlinkとは独立して、NETLINK_NETFILTER上のctnetlinkを使用します。
bpftooleBPFプログラム、マップ、リンク、BTF、cgroup、および選択されたネットワークアタッチメントをロードおよび検査します。ほとんどのオブジェクトライフサイクル操作では、libbpfとbpf()システムコールを使用します。一部のネットワーク操作では、rtnetlinkで管理されるXDPおよびトラフィック制御状態も検査または変更します。
FRRouting and BIRDBGP、OSPF、IS-IS、RIPなどのルーティングプロトコルを実装し、学習したルートをカーネルFIBと調整します。FRRoutingのプロトコルデーモンはzebraデーモンにルートを送信し、zebraがrtnetlinkを通じてカーネルを設定します。BIRDはLinux上で、ルーティングソケットまたはNetlinkを通じて独自のカーネルプロトコル同期を実行します。どちらも定常状態のルートインストールにip実行ファイルを必要としません。
Open vSwitch仮想化、コンテナ、オーバーレイ、ソフトウェア定義ネットワーキング向けのプログラム可能な仮想スイッチングを実装します。ovs-vsctlはOVSデータベースを変更し、ovs-vswitchdはその設定を消費して、OVS Generic Netlinkファミリーを通じてLinux OVSデータパスを制御します。補助的なリンクおよびトンネル設定ではrtnetlinkも使用される場合があります。
CNI plugins対応するランタイムがプラグインを呼び出したときに、コンテナネットワーク名前空間を設定します。一般的なプラグインはvethペア、ブリッジ、ルート、ポリシー、オーバーレイを作成します。プラグインは短時間実行のプログラムとして動作し、通常はGo Netlinkライブラリを直接使用します。プラグインはファイアウォール、eBPF、IPAM、データストアコンポーネントを追加で呼び出すかリンクする場合があります。CNIは単一のカーネルバックエンドではなく、呼び出しと結果の形式を規定します。
net-tools旧来のifconfig、route、arp、netstatコマンドを提供します。ツールは主にネットワークデバイスおよびルーティングioctlを使用し、procfsを解析します。新しい自動化では、iproute2と構造化されたNetlinkインターフェースがこれらに取って代わります。

この図は、一般的なnmcliの依存関係に関する疑問に直接答えます。

  1. nmcliはlibnmを通じて要求を構築します。
  2. libnmはD-Bus経由で要求をNetworkManagerデーモンに送信します。
  3. NetworkManagerは独自のNetlink実装を通じて、通常のカーネルネットワーク状態を適用します。
  4. iproute2は同じカーネルAPIの独立した管理クライアントであり、NetworkManagerとカーネルの間の中間層ではありません。

シェル自動化では、プログラムからip、nft、または別のCLIを呼び出すことが依然として有用です。ただし、長時間実行されるマネージャーは一般にライブラリを使用するか、カーネルプロトコルを直接実装します。直接アクセスによってコマンド出力の解析を避けられ、マネージャーは非同期状態通知を購読できます。
