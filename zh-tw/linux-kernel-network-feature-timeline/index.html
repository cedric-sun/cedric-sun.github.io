Linux 網路功能透過主線版本的漸進式發布演進，而不是透過獨立的子系統版本發布。以下里程碑標示了首次包含各項功能的穩定核心版本；後續核心可能會增加協定涵蓋範圍、驅動程式、卸載功能或使用者空間介面。

核心與使用者空間邊界 #

Linux 不提供add_route()或create_veth()之類的系統呼叫。相反地，使用者空間選擇核心控制介面，並透過通用系統呼叫存取它。尤其需要注意，Netlink 是一組通訊端協定，而不是系統呼叫。

SyscallsControl InterfaceNetwork Configuration RoleCurrent Guidance
socket(), bind(), sendmsg(), and recvmsg()Netlink程序開啟一個AF_NETLINK通訊端，並與某個 Netlink 家族交換結構化訊息。NETLINK_ROUTE設定連結、位址、路由、鄰居、流量控制及相關物件。Generic Netlink 和子系統協定涵蓋 nftables、nl80211、ethtool、devlink、WireGuard 等設施。對系統級網路設定，優先使用相關的 Netlink 家族。訊息屬性、確認、分段回覆和 API 演進都需要謹慎處理，因此應使用受維護的函式庫或工具。

大多數管理操作要求在管理目標網路命名空間的使用者命名空間中擁有CAP_NET_ADMIN。根據程式類型、附加點和核心版本，eBPF 操作還可能需要CAP_BPF、CAP_PERFMON或其他能力。

建議介面的變化 #

  1. 早期 Linux 使用 ioctl、通訊端選項和虛擬檔案。 ifconfig、route和arp等程式發出網路裝置和路由 ioctl。/proc/sys/net提供全域調節項，而透過舊版 iptables 設定的各代防火牆使用協定特定的通訊端選項。
  2. Rtnetlink 成為可擴充的網路控制平面。 Linux 2.2 透過NETLINK_ROUTE公開連結、多個位址、路由、鄰居和流量控制物件。因此，iproute2 工具（ip、bridge和tc）取代了面向 ioctl 的 net-tools 命令，用於新的設定。
  3. 子系統特定的 Netlink 家族取代了固定的私有 ABI。 Generic Netlink 及相關協定允許命令和類型-長度-值屬性在不變更系統呼叫的情況下演進。nl80211 取代 Wireless Extensions，nftables 取代舊版 iptables 規則 ABI，而較新的 ethtool 操作使用 Netlink 而不是裝置 ioctl。
  4. eBPF 增加了可程式化的資料平面邊界。 bpf()系統呼叫管理程式和對映，但設定仍依附加點劃分：rtnetlink 設定流量控制和既有的 XDP 附加，通訊端選項附加傳統通訊端過濾器，而 BPF 連結為受支援的掛鉤提供檔案描述元生命週期管理。
  5. 新的控制平面偏好描述完整的 Netlink API。 目前的核心網路開發透過機器可讀規格記錄 Netlink 家族。應用程式應使用這些 API，要求確認和擴充確認，並僅在不存在受支援的結構化替代介面時使用 ioctl 或文字檔案解析。

如需相應 UAPI 的詳細資料，請參閱核心的Netlink 介紹、rtnetlink(7)、netdevice(7)和bpf(2)文件。

Rtnetlink #

rtnetlink 中的rt表示routing，但該介面已發展為核心的一般網路控制協定。程序開啟socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE)並傳送RTM_*訊息。每則訊息包含struct nlmsghdr、物件特定的固定標頭，以及對齊的類型-長度-值屬性。

Rtnetlink 支援三種互動模式：

  • Do request: 建立、取代、變更或刪除一個物件，並接收確認。
  • Dump request: 列舉某個物件類別，例如所有連結或所有路由。核心會回傳以NLMSG_DONE結束的多部分回應。
  • Multicast notification: 訂閱連結、位址、路由、鄰居、規則、流量控制及其他變更的群組。通知使用與回覆相同的物件訊息，因此程式可以維護本機快取。

命名空間與一致性模型 #

rtnetlink 通訊端在其所屬的網路命名空間中運作。因此，大多數要求只能查看和修改該命名空間中的連結、路由、規則、鄰居和流量控制物件。連結屬性可以將裝置移到另一個命名空間，而命名空間 ID 訊息可以建立對等命名空間的參照。

變更要求通常需要在擁有目標網路命名空間的使用者命名空間中具備CAP_NET_ADMIN。當讀取要求暴露敏感的裝置或協定資訊時，也可能受到限制。

傾印不是原子快照。在多部分傾印進行期間，物件可能會變更；當接收緩衝區溢位時，多播通知可能遺失。狀態同步器應：

  1. 開啟通訊端並將其繫結到必要的多播群組。
  2. 使用唯一的序號要求傾印。
  3. 根據序號和傳送者連接埠 ID 比對單播回覆。
  4. 處理傾印期間到達的通知。
  5. 偵測ENOBUFS、中斷的傾印和格式錯誤的屬性。
  6. 當無法證明同步完成時，丟棄快取並重複傾印。

權威的操作清單定義於include/uapi/linux/rtnetlink.h。核心也為連結、位址、路由、規則、鄰居和流量控制發布了機器可讀規格。較高階的程式應使用受維護的函式庫或 iproute2，而不是手動重現 UAPI 結構配置和屬性驗證。

使用者空間網路工具 #

Linux 沒有單一的使用者空間網路堆疊。命令列工具、原則守護程式、設定轉譯器、路由守護程式和容器外掛程式會存取不同的核心控制介面。因此，較高階的命令可能控制的是守護程式，而不是直接聯絡核心。

SoftwarePrimary RolePath to the Kernel
iproute2ip管理連結、位址、路由、規則、鄰居和網路命名空間；bridge管理橋接器狀態；tc管理流量控制；ss檢查通訊端。這些程式直接使用 iproute2 的內部 Netlink 支援。大多數設定透過 rtnetlink 完成；通訊端檢查使用診斷用 Netlink 家族。iproute2 是一組可執行檔，而不是其他網路管理器所需的守護程式。
NetworkManager維護乙太網路、Wi-Fi、行動寬頻、VPN、IP 設定和 DNS 整合的連線設定檔與原則。nmcli、nmtui、桌面小程式和應用程式都是用戶端。nmcli使用 libnm，透過 D-Bus 呼叫 NetworkManager 守護程式。守護程式的 Linux 平台層會直接開啟 Netlink 通訊端，執行一般連結、位址、路由、規則和流量控制操作；它不會透過ip可執行檔傳送這些操作。選用的輔助程式處理 Wi-Fi 驗證、PPP、DHCP、DNS 和防火牆整合等設施。
systemd-networkd套用宣告式的.network、.netdev和.link設定，執行 DHCP 和路由器探索用戶端，並維護網路狀態。networkctl是其檢查和控制 CLI。systemd-networkd使用 systemd 內部的 Netlink 實作設定核心。對受管理設定而言，networkctl使用 networkd API 和狀態，而不是呼叫 iproute2。
Netplan將發行版層級的 YAML 轉換為後端設定，並協調套用該設定。Netplan 選擇 NetworkManager 或 systemd-networkd 作為轉譯器。持續執行核心設定的是選取的守護程式，而不是 Netplan 的 YAML 剖析器。
nftablesnft建立防火牆、NAT、封包分類以及集合或對映規則。libnftables 向應用程式公開相同的引擎。nft使用 libnftables 和 libnftnl，透過NETLINK_NETFILTER與 nftables 子系統交換批次訊息；它不使用 rtnetlink 或 iproute2。
firewalld維護動態防火牆區域、服務、原則以及獨立的執行階段和永久設定。firewall-cmd是其主要 CLI。firewall-cmd透過 D-Bus 呼叫 firewalld 守護程式。守護程式通常透過 nftables 後端套用規則，而不是要求 NetworkManager 或 iproute2 安裝規則。
ethtool讀取和變更驅動程式與 NIC 屬性，例如連結模式、通道、環、合併、卸載、RSS、統計資料和韌體資料。較新的操作使用 ethtool Generic Netlink 家族。較舊或尚未轉換的操作使用SIOCETHTOOL ioctl，因此所選路徑取決於命令和核心支援。
iw檢查和設定 802.11 實體裝置、虛擬介面、頻道、站台、掃描、省電和法規狀態。iw向nl80211 Generic Netlink 家族傳送命令。它不會呼叫ip，但產生介面的普通連結和 IP 層設定仍由ip負責。
wpa_supplicant and iwd執行 Wi-Fi 掃描、驗證、關聯、漫遊和金鑰管理。每個守護程式都透過nl80211控制 cfg80211/mac80211。NetworkManager 可以透過 D-Bus 控制任一守護程式；接著由 Wi-Fi 守護程式與核心通訊。
conntrack-tools列出、修改、監視和複製 Netfilter 連線追蹤狀態。conntrack和conntrackd使用NETLINK_NETFILTER上的 ctnetlink，獨立於 rtnetlink 運作。
bpftool載入和檢查 eBPF 程式、對映、連結、BTF、cgroup 以及選定的網路附加。大多數物件生命週期操作使用 libbpf 和bpf()系統呼叫。部分網路操作也會檢查或修改由 rtnetlink 管理的 XDP 和流量控制狀態。
FRRouting and BIRD實作 BGP、OSPF、IS-IS 和 RIP 等路由協定，並將學習到的路由與核心 FIB 協調。FRRouting 協定守護程式將路由提交給其zebra守護程式，由後者透過 rtnetlink 設定核心。BIRD 在 Linux 上透過路由通訊端或 Netlink 執行自己的核心協定同步。兩者在穩定狀態下安裝路由都不需要ip可執行檔。
Open vSwitch為虛擬化、容器、覆蓋網路和軟體定義網路實作可程式化的虛擬交換。ovs-vsctl修改 OVS 資料庫；ovs-vswitchd消費該設定，並透過 OVS Generic Netlink 家族控制 Linux OVS 資料路徑。輔助連結和通道設定也可能涉及 rtnetlink。
CNI plugins當相容的執行階段呼叫外掛程式時，設定容器網路命名空間。常見外掛程式會建立 veth 對、橋接器、路由、原則和覆蓋網路。外掛程式以短生命週期程式執行，通常直接使用 Go Netlink 函式庫。外掛程式還可能額外呼叫或連結防火牆、eBPF、IPAM 或資料儲存元件；CNI 規定的是呼叫和結果格式，而不是單一核心後端。
net-tools提供舊版的ifconfig、route、arp和netstat命令。這些工具主要使用網路裝置和路由 ioctl，並解析 procfs。對於新的自動化，iproute2 和結構化 Netlink 介面已取代它們。

此圖直接回答常見的nmcli依賴問題：

  1. nmcli透過libnm建構要求。
  2. libnm 透過D-Bus將要求傳送給NetworkManager 守護程式。
  3. NetworkManager 透過自身的 Netlink 實作套用一般核心網路狀態。
  4. iproute2 是相同核心 API 的獨立管理用戶端，不是 NetworkManager 與核心之間的中介層。

在 shell 自動化中，從程式呼叫ip、nft或其他 CLI 仍然有用，但長時間執行的管理器通常使用函式庫，或直接實作核心協定。直接存取可以避免解析命令輸出，並讓管理器訂閱非同步狀態通知。
